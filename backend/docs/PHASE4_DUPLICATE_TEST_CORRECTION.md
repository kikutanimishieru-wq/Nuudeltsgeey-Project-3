# Phase 4 duplicate-participation concurrency test correction

Local preparation only. Ready for a newly authorized disposable branch; no native database test has validated this correction yet. The prior failure's exact cause remains UNKNOWN. No schema, migration, application service or governance changes.

The native direct-write test no longer asserts String(error) contains a literal PostgreSQL exception. It requires two distinct simultaneous session IDs, exactly one fulfilled transaction and one rejection, then validates committed postconditions and the rejection's structured details. The parent registration is created through Prisma; the roster child is inserted with parameterized tagged SQL within the same transaction. This preserves the intended registration/roster trigger path and atomic rollback while allowing raw Prisma P2010 metadata to retain PostgreSQL code/message context.

The fixture must start without registrations, have two distinct teams containing the same player, and have all four relevant registration/roster guard and invariant triggers enabled and bound to their expected functions. The launcher still verifies the complete checksum-pinned schema before any fixture execution.

Expected rejection requires PostgreSQL 23505 or Prisma P2002, plus a recognized duplicate-specific context: the exact DUPLICATE_TOURNAMENT_PARTICIPATION marker or structured PostgreSQL WHERE identifying enforce_phase4_entrant_invariants. Generic/unattributed P2002 and 23505 fail. A named unrelated constraint or populated Prisma target fails; this trigger is not a named cross-team unique index. Conflicting or unrecognized structured codes fail, including timeout, connection, deadlock, serialization and transaction-expiration codes. No rejection is accepted merely because one competing transaction failed. SQLSTATE is reported only when actually present; P2002 is never relabeled as an observed 23505.

Postconditions require one total event registration, one total roster member, zero duplicate roster entries, the registered team matching the fulfilled transaction's team, and the sole roster member matching the shared fixture player. A failed child write must not leave a second parent registration. This test deliberately isolates cross-team participation using one roster member per entrant; it does not certify a complete valid 2v2 roster.

Diagnostics use fixed stages: FIXTURE_CONTEXT, SESSION_STARTED, TRANSACTION_OUTCOMES, DISTINCT_SESSIONS, ONE_COMMIT, DATABASE_POSTCONDITIONS, REJECTION_CONTEXT and COMPLETE. Stage records are flushed before assertions and session IDs are recorded before barrier waiting. They contain only numeric session IDs, fixed outcome tokens, booleans/counts, allowlisted Prisma/SQLSTATE codes, rejection-context tokens and an unexpected-code flag. No fixture IDs, names, URLs, raw messages, assertion values, stacks or credentials are written. The Python parent independently rebuilds the same allowlisted fields into the retained private report. Per-test durations and ordinary reporter results remain available. A P2002 is categorized as DATABASE_CONSTRAINT for diagnostics; that category alone never passes the concurrency assertion.

ReadCommitted isolation, bounded barriers/transactions/locks, exact branch/direct endpoint verification, strict TLS, process-group termination, retry=0 and bail=1 are preserved. A new branch still needs separate identity verification and explicit guard retargeting; the populated v2 branch cannot pass the empty-database startup guard. No automatic retry, cleanup or retargeting was introduced.
